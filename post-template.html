Writing a Cycle-Accurate RISC-V Pipeline in C99

Most introductory CPU emulators execute instructions in a single giant switch loop: fetch 32 bits, decode the opcode, mutate the register file, and increment pc. That works if you just want to run Doom, but it hides the most interesting part of hardware design—data hazards, forwarding paths, and branch penalties.

For riscv-emu, I wanted a cycle-accurate 5-stage pipeline (IF → ID → EX → MEM → WB) in portable C99 that compiles to both native x86_64 and WebAssembly.

Double-Buffered Pipeline latches

In hardware, flip-flops between pipeline stages latch on the rising clock edge. If you update pipeline registers in-place in C from IF to WB, later stages immediately see values produced in the same clock cycle. Instead, we keep two copies of each inter-stage latch and step backwards: 

typedef struct {
    uint32_t pc;
    uint32_t ir;
    uint8_t  rd, rs1, rs2;
    int32_t  imm;
    bool     valid;
} latch_id_ex_t;

void cpu_tick(cpu_t *cpu) {
    // Compute next state from current latches
    stage_wb(cpu);
    stage_mem(cpu);
    stage_ex(cpu);
    stage_id(cpu);
    stage_if(cpu);

    // Commit latches on rising edge
    cpu->if_id  = cpu->next_if_id;
    cpu->id_ex  = cpu->next_id_ex;
    cpu->ex_mem = cpu->next_ex_mem;
    cpu->mem_wb = cpu->next_mem_wb;
    cpu->cycles++;
}

Load-Use Hazard Stalling

Arithmetic instructions can bypass their result directly from the EX/MEM or MEM/WB latch back into the ALU inputs. However, a lw (load word) instruction doesn't produce data until the end of MEM. When the instruction in ID reads a register being loaded in EX, we have to freeze PC and IF/ID for one cycle and inject a NOP bubble into ID/EX: 

bool load_use_hazard = cpu->id_ex.mem_read &&
    cpu->id_ex.rd != 0 &&
    (cpu->id_ex.rd == rs1 || cpu->id_ex.rd == rs2);

if (load_use_hazard) {
    cpu->next_if_id = cpu->if_id;       // Freeze IF/ID
    cpu->next_id_ex = (latch_id_ex_t){0}; // Insert bubble
    return;
}

Results on CoreMark

Adding full EX→EX and MEM→EX forwarding dropped the average CPI on Dhrystone and CoreMark from 1.84 down to 1.19, with the remaining overhead coming from static branch-not-taken flushes. Next up: a 2-bit saturating counter branch target buffer.
